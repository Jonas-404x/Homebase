# Mainframe Teil 3.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Status overview, per-app CPU/RAM/disk, a diagnose button, the missing RAM warning, a stricter service check, and a Windows desktop app.

**Architecture:** Server gets pure, unit-tested builders (`status/collect.ts`, `diagnose/*.ts`, `apps/usage.ts`) fed by small adapters (dockerode, existing stores). Web shows them on Übersicht, Apps, Details and Dienste. The desktop app is a separate Electron workspace (`apps/desktop`) that only wraps the web UI.

**Tech Stack:** Fastify 5, node:sqlite, dockerode, React 19, vitest; Electron + electron-builder for the desktop app.

**Spec:** docs/superpowers/specs/2026-11-25-mainframe-ausbau-design.md, section "Teil 3.1".

## Global Constraints

- UI German, README/CHANGELOG English. Public repo: no real IPs, MACs, names, emails, secrets in code/tests/docs (example 192.168.1.x only).
- Tests switch off all background timers (`testDeps()`); no test touches the real network or Docker.
- Status levels exactly: `problem` (rot), `warn` (gelb), `info` (grau); summary `ok` / `warn` / `problem` from the worst non-info item.
- Service OK = HTTP 2xx, 3xx, 401, 403; or TCP connect. Apps additionally need container running and, if a healthcheck exists, healthy.
- Every diagnose step: `ok: true | false | null` (null = skipped), one sentence `detail`, one sentence `fix` when not ok.

## Review Focus

1. Docker not running: status, usage and diagnose must answer quickly with a clear "Docker läuft nicht" item, never hang or 500.
2. An app the user stopped on purpose is a `info`, not a `problem`; an app that exited with a non-zero code or keeps restarting is a `problem`.
3. CPU % from a one-shot docker stats with missing `precpu_stats` (first sample) must be 0, not NaN/Infinity.
4. A login page (401/403) still counts as working; a 404/502 does not, and the tile says why.
5. The desktop app never exposes its preload API to the remote web UI and never navigates away from the configured origin.

### Task 1: RAM-Warnung
- Modify `apps/server/src/system/warnings.ts`: check `memory` percent (`usedBytes/totalBytes*100`) against `t.memory`, text `Arbeitsspeicher zu ${n} % belegt`.
- Test in `apps/server/test/warnings.test.ts` (or existing file): 95 % with threshold 90 → one warn event; staying at 95 → no second; 80 → re-armed.

### Task 2: Docker-Werte pro App (`apps/server/src/apps/usage.ts`)
- Pure: `cpuPercent(stats)`, `memBytes(stats)` (usage minus `inactive_file`/`cache`), `diskByApp(df, label)` (container `SizeRw` + volumes whose `com.docker.compose.project` equals the app's project, keyed by `mainframe.app` label).
- `DockerStatus` gains `usage(): Promise<Map<string,{cpuPercent,memBytes}>>`, `disk(): Promise<Map<string,number>>`, `inspect(appId)` → `{ containers: {name,state,health,restartCount,exitCode,startedAt}[], logs: string[] }` (last 50 lines).
- Shared type `AppUsage { appId; cpuPercent; memBytes; diskBytes: number | null }`.
- Route `GET /api/apps/usage` → `AppUsage[]`; disk cached 60 s; Docker down → `[]`.
- Tests: fixtures for stats JSON (incl. first sample without precpu → 0), df JSON; route with fake engine.

### Task 3: Genauere Dienstprüfung
- `checkUrl` returns `{ ok, ms, reason: string | null }`; reasons: `Antwortet mit Fehler <code>`, `Zeitüberschreitung`, `Verbindung abgelehnt`, `Nicht erreichbar`.
- OK statuses: 2xx, 3xx, 401, 403.
- App targets: if container not running → `Container gestoppt`; unhealthy → `Container meldet „ungesund“` (health from `containersByApp`, parsed from list `Status` "(unhealthy)").
- `ServiceStatus.reason: string | null` (last result, kept in memory by the checker).
- Tests: 404 → down with reason; 401 → up; unhealthy app → down with reason.

### Task 4: Statusübersicht (`apps/server/src/status/`)
- Pure `collectStatus(input)` → `StatusReport { level, summary, items: StatusItem[] }`; `StatusItem { id, level, title, detail, to: string | null, diagnose: string | null }`.
- Inputs: docker ok, apps (state/error), services (up/reason), internet online, latest stats + thresholds, unknown devices count, 2FA enabled.
- Summary text: `Alles läuft`, `1 Sache braucht dich`, `N Sachen brauchen dich`.
- Route `GET /api/status`.
- Tests: each source, ordering (problem → warn → info), info-only → `ok`.

### Task 5: Diagnose (`apps/server/src/diagnose/`)
- `diagnoseApp(facts)` and `diagnoseSystem(facts)` pure → `DiagnoseReport { target, ok, steps: DiagnoseStep[] }`; `DiagnoseStep { id, label, ok, detail, fix, action: {kind:'restart-app', appId} | {kind:'link', to, label} | null }`.
- App steps: Docker, Container läuft, Neustarts/Exit-Code, Fehler im Log (lines matching `error|fatal|exception|panic` case-insensitive, show up to 3), Port offen, Weboberfläche, Speicherplatz, RAM.
- System steps: Docker, each app (summary), Dienste, Internet (probe) + DNS (`dns.lookup('cloudflare.com')`), Laufwerke, RAM, Temperatur.
- Routes `POST /api/diagnose` and `POST /api/apps/:id/diagnose`; facts gathering in small adapter with injectable deps; rate-limited.
- Tests: crash-looping app explains exit code and offers restart; healthy app all ok; Docker down short-circuits remaining steps to skipped.

### Task 6: Oberfläche
- Übersicht: `StatusPanel` at the top (summary line + items with link/diagnose buttons, „Alles prüfen“ button) polling `/api/status` every 15 s.
- `DiagnoseDialog` (shared): runs the diagnose, shows steps with ok/problem/skipped icons + text, action buttons.
- Apps page: per app CPU %, RAM, Speicher (from `/api/apps/usage`, every 5 s) and a „Diagnose“ button.
- Details (CPU/RAM): section „Apps“ listing usage sorted by the page's metric.
- Dienste tile: reason under the status when down.
- Tests in `apps/web/test/status.test.tsx` and existing apps/services tests.

### Task 7: Windows-App (`apps/desktop`, by Codex, reviewed by Claude)
- Electron wrapper as specified in the Codex brief (address config, offline page, tray, single instance, navigation lock, preload only on local page).
- `node --test` for `normalizeAddress`. Root script `desktop:dist`.
- Verify: `npm run dist -w apps/desktop` builds `Mainframe Setup *.exe`; start it, it shows Mainframe.

### Task 8: Abschluss
- README/CHANGELOG (English), build, restart Mainframe, browser check desktop + 375 px, final review (fresh opus reviewer + Codex second opinion), fix, PR into main, merge.
